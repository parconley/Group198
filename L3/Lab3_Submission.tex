The Address Resolution Protocol (ARP) is a fundamental protocol in computer networks that translates IP addresses to MAC (hardware) addresses. This experiment explores ARP behavior  including basic request/response mechanisms, caching, neighbor reachability detection, and the ARP state machine.

\subsubsection*{Questions and Answers}

Q1: Why was ARP sent in the first case but not the second?

In the first case (pc-a-arp.pcap), the ARP table was empty after being flushed. PC-A had no knowledge of PC-B's MAC address, so it sent an ARP Request to resolve 10.0.0.101 to a MAC address before sending the ICMP Echo Request.

In the second case (pc-a-no-arp.pcap), the ARP entry for 10.0.0.101 was already cached in PC-A's neighbor table from the previous ping. Since PC-A already knew the MAC address (00:4e:01:bd:77:59), no ARP resolution was necessary.

\vspace{0.5cm}
Q2: What is the target IP address in the ARP Request?

The target IP address is 10.0.0.101 (PC-B's IP address). This is visible in the ARP Request message: "who-has 10.0.0.101 tell pc-a"

\vspace{0.5cm}
Q3: What is the destination MAC address in the ARP Request frame?

The destination MAC address is ff:ff:ff:ff:ff:ff (the broadcast MAC address). ARP Requests are always broadcast because the sender does not yet know the target's MAC address and needs all hosts on the local network to receive and process the request.

\vspace{0.5cm}
Q4: What is the value of the frame type field in the Ethernet frame?

The EtherType field value is 0x0806, which identifies the frame as containing an ARP packet. This is the standard EtherType value for ARP frames.

\vspace{0.5cm}
Q5: At the end of the exchange, which hosts learned from the ARP Request, and which hosts learned from the ARP Reply?

From the ARP Request, PC-B learned PC-A's MAC address (00:4e:01:be:5c:34) and IP address (10.0.0.100). Even though the request was broadcast, PC-B processed it becuase it was the target, and  proactively cached PC-A's information. From the ARP Reply, only PC-A learned the information. The reply was unicast directly to PC-A (destination MAC: 00:4e:01:be:5c:34), informing it that 10.0.0.101 is at MAC address 00:4e:01:bd:77:59.

The packet capture shows that approximately 5 seconds later, PC-B sends its own ARP Request to verify PC-A's reachability, confirming that both hosts successfully learned each other's MAC addresses.

\subsubsection*{Questions and Answers}

Q1: What is the target IP address in the ARP Request?

The target IP address is 10.0.0.101 (PC-B). This is the host whose reachability PC-A is verifying.

\vspace{0.5cm}
Q2: What is the destination MAC address of the ARP Request? Is it a broadcast or unicast address?

The destination MAC address in this ARP Poll is 00:4e:01:bd:77:59 (PC-B's MAC address), which is a unicast address.

This is fundamentally different from a regular ARP Request, which uses the broadcast address (ff:ff:ff:ff:ff:ff). The unicast destination proves this is an ARP Poll used for neighbor reachability verification rather than initial MAC address resolution.

\vspace{0.5cm}
Q3: How is this different than the ARP Request observed in Exercise 1.2?

\begin{table}[H]
\centering
\begin{tabular}{|p{3cm}|p{5cm}|p{5cm}|}
\hline
Aspect & Exercise 1.2 (Regular ARP) & Exercise 1.3 (ARP Poll) \\
\hline
Purpose & Resolve unknown MAC address & Verify neighbor still reachable \\
\hline
Destination MAC & ff:ff:ff:ff:ff:ff (broadcast) & 00:4e:01:bd:77:59 (unicast) \\
\hline
Sender's Knowledge & Doesn't know target's MAC & Already knows target's MAC \\
\hline
Timing & Immediate when cache empty & Periodic/when entry aging out \\
\hline
ARP Cache State & NONE to INCOMPLETE to REACHABLE & REACHABLE to DELAY to PROBE to REACHABLE \\
\hline
\end{tabular}
\caption{Comparison of Regular ARP vs. ARP Polling}
\end{table}

In Exercise 1.2, PC-A had no ARP entry and needed to discover PC-B's MAC address, requiring a broadcast. In Exercise 1.3, PC-A's ARP entry for PC-B was expiring (REACHABLE state timing out), so it sent a unicast ARP Request directly to PC-B's known MAC address to verify PC-B is still reachable and refresh the cache entry.

This demonstrates Linux's Neighbor Unreachability Detection (NUD) mechanism, which uses unicast ARP probes to verify cached entries without flooding the network with broadcasts.

\subsubsection*{Questions and Answers}

Q1: In the packet capture, did you see an ICMP Echo Request sent from PC-A to the non-existent host, or only ARP Requests? Why?

Only ARP Requests were observed. No ICMP Echo Request was sent because the network stack cannot send an IP packet without first resolving the destination's MAC address. Since ARP resolution failed after 3 attempts, the IP layer never sent the ICMP packet.

\vspace{0.5cm}
Q2: How many attempts did PC-A make to resolve the MAC address, and what was the timeout between attempts?

PC-A made 3 ARP Request attempts with approximately 1 second timeout between attempts (17:36:05.151575, 17:36:06.206004, 17:36:07.229998). After the third failed attempt, the neighbor entry transitioned to the FAILED state.

\vspace{0.5cm}
Q3: On the loopback interface, observe that an ICMP Destination Host Unreachable message was sent from PC-A to itself. Explain why this occurred and what triggers this message.

When ARP resolution failed after 3 attempts, the kernel generated an ICMP Type 3 Code 1 (Host Unreachable) message. This message appears on the loopback interface because it's being delivered internally to the \texttt{ping} process on PC-A itself, allowing the application to receive feedback about the unreachable destination.

\subsubsection*{Transition 1: NONE to INCOMPLETE to REACHABLE}

Screenshot 1: State transition from NONE to REACHABLE

\begin{figure}[H]
\centering

\caption{Packet capture showing NONE to INCOMPLETE to REACHABLE state transition}
\end{figure}

The ARP Request (NONE to INCOMPLETE) is a broadcast request asking "who-has 10.0.0.101 tell 10.0.0.100" with destination ff:ff:ff:ff:ff:ff (broadcast). The ARP Reply (INCOMPLETE to REACHABLE) replies "10.0.0.101 is-at 00:4e:01:bd:77:59" as a unicast response to PC-A. The ICMP Echo Request/Reply now occurs in REACHABLE state. Bidirectional verification occurs approximately 5 seconds later.

The first state is NONE where no ARP entry exists. The second state is INCOMPLETE where an ARP Request has been sent and the system is waiting for a reply. The third state is REACHABLE where an ARP Reply has been received and the entry is valid and confirmed reachable.

\subsubsection*{Transition 2: DELAY to PROBE to REACHABLE}

Screenshot 2: State transition showing ARP polling

\begin{figure}[H]
\centering
\includegraphics[width=0.9\textwidth]{"Lab 3 - USB Stuff/e1.5 head pc-delay-to-probe.png"}
\caption{Packet capture showing DELAY to PROBE to REACHABLE transition with unicast ARP polling}
\end{figure}

The ICMP Echo Request/Reply triggers the DELAY state. The unicast ARP Request (DELAY to PROBE, approximately 5 seconds later) asks "who-has 10.0.0.101 tell 10.0.0.100" where the key observation is that the destination MAC is unicast 00:4e:01:bd:77:59 (not broadcast). The ARP Reply (PROBE to REACHABLE) follows. Bidirectional verification is also demonstrated.

The first state is DELAY where the ARP entry exists but is aging and waiting for upper-layer confirmaton. The second state is PROBE where the entry is expiring and a unicast ARP probe is sent to verify the neighbor is still reachable. The third state is REACHABLE where the probe response has been received, the entry is refreshed, and the neighbor is confirmed reachable.

The unicast ARP Request (destination MAC: 00:4e:01:bd:77:59, not broadcast) demonstrates the PROBE state. This is ARP polling to refresh an aging cache entry, not initial discovery.

\subsection{Exercise 2.2: Learning MAC Addresses}

\subsubsection*{Ordered List of 6 Events}

Event 1: Romeo sends ARP Request (Broadcast)

Romeo doesn't know Juliet's MAC address, so it broadcasts an ARP Request asking "who-has 10.0.0.101?" The destination MAC is ff:ff:ff:ff:ff:ff (broadcast). The bridge floods the ARP Request out all ports except the incoming port (port 1). All hosts recieve  the broadcast request.

\vspace{0.5cm}
Event 2: Bridge learns Romeo's MAC address

When the ARP Request arrives at the bridge on port 1, the bridge examines the source MAC field and learns Romeo's location. The bridge MAC table is updated with Port 1 to 02:0e:2f:76:d5:6d (Romeo). The ageing timer starts (typically 300 seconds). The entry is marked as "learned" (not local).

\vspace{0.5cm}
Event 3: Juliet receives ARP Request and sends ARP Reply (Unicast)

Juliet receives the broadcast ARP Request on port 2 and replies with a unicast ARP Reply containing her MAC address. The ARP Reply states "10.0.0.101 is-at 02:03:a9:83:3a:9b". The destination MAC is 02:0e:2f:76:d5:6d (Romeo's MAC - unicast). The bridge forwards to port 1 only because it knows Romeo is on port 1 from Event 2.

\vspace{0.5cm}
Event 4: Bridge learns Juliet's MAC address

When the ARP Reply arrives at the bridge on port 2, the bridge examines the source MAC field and learns Juliet's location. The bridge MAC table is updated with Port 2 to 02:03:a9:83:3a:9b (Juliet). The ageing timer starts. The entry is marked as "learned".

\vspace{0.5cm}
Event 5: Romeo sends ICMP Echo Request (Unicast)

Romeo now knows Juliet's MAC address from the ARP Reply, so it sends an ICMP Echo Request directly to Juliet. The ICMP packet flows from 10.0.0.100 to 10.0.0.101. The source MAC is 02:0e:2f:76:d5:6d. The destination MAC is 02:03:a9:83:3a:9b. The bridge forwards to port 2 only because it knows Juliet is on port 2 from Event 4.

\vspace{0.5cm}
Event 6: Juliet sends ICMP Echo Reply (Unicast)

Juliet responds with an ICMP Echo Reply back to Romeo. The ICMP reply flows from 10.0.0.101 to 10.0.0.100. The source MAC is 02:03:a9:83:3a:9b. The destination MAC is 02:0e:2f:76:d5:6d. The bridge forwards to port 1 only because it knows Romeo is on port 1.

\subsubsection*{Key Observations}

The bridge learns MAC addresses from the source MAC field of incoming frames. Learning occurs on the first frame from each host. Learned entries have an ageing timer of 300 seconds.

Before learning, the bridge broadcasts or floods unknown destinations to all ports. After learning, it forwards unicast frames only to the specific port where the destination is located. This efficiency reduces unnecessary traffic on other ports, meaning Hamlet and Ophelia don't see Romeo-Juliet unicast traffic after learning.

iperf3 Performance Test from Romeo to Juliet

The measured throughput (~1.16 Mbits/sec sender, 947 Kbits/sec receiver) is lower than the theoretical maximum due to CloudLab resource constraints and virtualization overhead. However, the experiment successfully demonstrates the bridge's forwarding capability.

In an ideal scenario with dedicated hardware, single session throughput would be approximately 940 Mbps for 1 Gbps links. Multiple simultaneous sessions achieve full throughput on non-overlapping port pairs. Total aggregate throughput can exceed line rate, for example 3 sessions × 940 Mbps = 2.82 Gbps.

\subsubsection*{Network Capacity Analysis}

Each port on the bridge is a seperate collision domain. This means that full-duplex operation allows each link to send and receive simultaneously at full line rate. Independent forwarding means the bridge can forward between different port pairs simultaneously. Additionally, there is no contention, so traffic from Port 1 to 2 does not interfere with Port 3 to 4.

\begin{table}[H]
\centering
\begin{tabular}{|p{4cm}|p{5cm}|p{5cm}|}
\hline
Aspect & Hub (Single Collision Domain) & Bridge (Multiple Collision Domains) \\
\hline
Collision Domains & 1 shared domain & 1 per port \\
\hline
Simultaneous Transmissions & Only one at a time & Multiple (different port pairs) \\
\hline
3 Sessions Throughput & ~313 Mbps each (1000/3) & ~940 Mbps each \\
\hline
Total Aggregate & ~1000 Mbps & ~2820 Mbps (3×940) \\
\hline
Efficiency & Low (shared medium) & High (microsegmentation) \\
\hline
\end{tabular}
\caption{Hub vs. Bridge Performance Comparison}
\end{table}

Microsegmentation creates multiple collision domains. Each port pair can operate at full duplex simultaneously. Total network capacity scales with the number of active port pairs. This provides significantly higher aggregate throughput than hubs.
